# View Caddy Logs — Design

**Date:** 2026-06-22
**Status:** Approved — ready for implementation plan
**Context:** First backend-led feature after the rnui UI program (M0–M6) + the read-only proxy details page (PR #32). Replaces the dropped B2 (per-proxy health) backlog item. Scope is **operational/debugging visibility**, not per-host monitoring.

## Goal

Let an admin **view Caddy's logs in the Waygates UI** — both Caddy's **runtime/error log** (startup, errors, TLS/cert events, reloads, upstream failures) and its **HTTP access log** (per-request) — as a **live stream** with filtering, for debugging and operational visibility.

## Context (current state)

Established by exploration of the running setup:

- **Caddy runs from a JSON config**, not a Caddyfile: `caddy run --config /etc/caddy/caddy.json` (`docker/entrypoint.sh`). The config is generated by `backend/internal/caddy/config/builder.go` (`Build()`), written to `/etc/caddy/caddy.json` by `file_manager.go`, and applied via the Caddy **admin API** `POST localhost:2019/load` (`reloader.go`).
- **Caddy currently persists no logs.** Its stdout/stderr go to the container's stdio (Docker logging driver) — not readable by the Go backend, not persisted in a file. The `CaddyConfig` struct already defines `Logging *LoggingConfig` (with `Logs` map → `Writer`/`Encoder`/`Level`) in `config/types.go`, but `builder.go` **never populates it**, and no HTTP server has access logging configured.
- The **admin API does not serve logs** (only config) — so logs must come from a file.
- **Paths/volumes:** `CADDY_BASE_PATH` (`/etc/caddy`), `CADDY_STORAGE_PATH` (`/data`); docker volumes `caddy-data:/data`, `caddy-config:/config`, `caddy-etc:/etc/caddy`. No log dir/volume exists yet.
- **Backend pattern:** handler → service → repository/reader; routes in `backend/internal/api/routes/routes.go` gated by `chimw.RequirePermission(authAdapter, "<key>", mwConfig)`; permissions declared in `backend/rbac.yaml` (e.g. `audit_logs:read`).
- **Caddy logs ≠ audit logs.** Waygates already has a DB-backed **audit log** (admin actions) surfaced at `/dashboard/activity`. This feature is unrelated — it surfaces Caddy's own runtime/access logs.
- **Frontend pattern:** dashboard routes registered in `ui/src/lib/router.tsx` (code-based, lazy by named export); sidebar nav in `ui/src/components/layout/sidebar.tsx`; the Activity page (`routes/_dashboard/activity.tsx`, `components/activity/`) is the rnui reference for a log/list view.

## Scope

**In:**
- Enable structured (JSON) file logging in the generated Caddy config: a **runtime** log (Caddy default logger) and an **access** log (HTTP servers), each rolled, written to a log volume.
- A backend **log tailer** + endpoints: an **SSE stream** (backfill + live tail) and a **snapshot** GET, under `/api/caddy-logs`, gated by a new `caddy_logs:read` permission.
- A new **`/dashboard/caddy-logs`** UI page (Runtime | Access tabs, live view, pause/resume, clear, client-side search/filter) + sidebar entry.
- Docker plumbing for the log volume.

**Out of scope:**
- **L4 (layer4) access logs** — the layer4 app's logging differs; L4 issues surface in the runtime log. (HTTP access logs only.)
- Per-host / per-proxy health monitoring (dropped B2). Client-side filtering of the log view by host is fine; continuous per-host status is not.
- Traffic metrics/aggregation (that is B3).
- Log search across historical rolled-and-deleted files / external log shipping.

## Architecture & data flow

```
builder.go populates config.Logging          Caddy (caddy.json)
  runtime → $CADDY_LOG_PATH/runtime.log   ──────────────────▶  writes rolled
  access  → $CADDY_LOG_PATH/access.log                          JSON log files
        │                                                          │
        ▼                                                          ▼
  Go tailer service (poll size ~500ms, detect rotation, reopen) ◀── log volume
        │   SSE: backfill last 500 + stream appends
        ▼
  /dashboard/caddy-logs  (Runtime | Access tabs, live viewer)
```

## Backend design

### Logging config (the foundational change — highest risk)
In `backend/internal/caddy/config/builder.go` `Build()`, populate `config.Logging.Logs` with two entries (JSON encoder):
- **runtime** — Caddy's default logger → file writer `$CADDY_LOG_PATH/runtime.log`, level `INFO`, with roll settings.
- **access** — a named logger (e.g. `log0`/`access`) → file writer `$CADDY_LOG_PATH/access.log`, JSON, rolled; wire HTTP servers to emit access logs to it (each HTTP server's `logs` config / a log `include` for the server access-log names). Apply to HTTP servers only.

Roll settings (from `LogConfig`/Caddy `roll` module): **`roll_size` 10 MiB, `roll_keep` 5, `roll_keep_days` 7**.

This must not break existing config generation, `caddy validate`, or the admin-API reload. The builder's existing tests are extended to assert the logging block is present and well-formed, and that a config with logging still validates.

### Log volume & paths
- New env var **`CADDY_LOG_PATH`** (default `/var/log/caddy`), read in `config` + passed into the builder (so the file writer paths are configurable and testable).
- `Dockerfile`: create the dir with correct ownership (the Caddy process must be able to write; the Go backend must be able to read). `docker-compose.yml`: add a `caddy-logs:/var/log/caddy` volume.

### Tailer service
`backend/internal/service/caddy_logs_service.go` (+ a `caddy/logtail` reader): a **poll-based tailer** (no new dependency) — open the file, seek to backfill the last N lines, then every ~500ms stat for size growth and read appended bytes; detect rotation (size shrink / inode change) and reopen. Parse each JSON line into a structured record (`ts`, `level`, `logger`, `msg`, plus access fields when present). Bound backfill to **last 500 lines**. Source = `runtime | access` selects the file.

### Endpoints (`/api/caddy-logs`, RBAC `caddy_logs:read`)
- `GET /api/caddy-logs/stream?source=runtime|access` — **SSE**: emit the backfill (last 500) then stream new lines as they are appended; clean up the tailer on client disconnect (context cancel).
- `GET /api/caddy-logs?source=runtime|access&limit=N` — **snapshot** of the last N lines (initial load / SSE fallback / tests).
- Handler `backend/internal/api/handlers/caddy_logs_handler.go`; routes registered in `routes.go`; new permission group in `rbac.yaml`:
  ```yaml
  - name: "Caddy Logs"
    permissions:
      - key: "caddy_logs:read"
        name: "View Caddy Logs"
        description: "View Caddy runtime and access logs"
  ```

### Auth (SSE) — important
The app authenticates with **JWT Bearer headers** (ky). Browser `EventSource` cannot set custom headers, so the **frontend SSE client uses `fetch` + `ReadableStream`** (not `EventSource`) to send `Authorization: Bearer …`; it parses the SSE event framing manually. The backend `RequirePermission` middleware is unchanged. (Do not pass the token via query string.)

## UI design

- New route `/dashboard/caddy-logs` (code-based in `router.tsx`, named-export lazy component) + a sidebar entry (`ScrollText`/similar lucide icon).
- Page: **Runtime | Access** tabs (rnui `Tabs`); a live monospace log view with **auto-scroll (pause on manual scroll-up)**, **Pause/Resume** stream, **Clear**, and **client-side search/filter** (runtime: by level + text; access: by status/host + text). Bounded in-memory buffer **~3000 lines** (drop oldest).
- Structured rendering: runtime row → `timestamp · level · message`; access row → `status · method · host · uri · duration`. Connection/error states (stream dropped → show a reconnect affordance).
- Data layer: a `use-caddy-logs` hook wrapping the fetch-stream SSE client (start/stop, buffer, filter); the snapshot endpoint for initial paint/fallback. Consistent with the Activity page's rnui patterns.

## Decisions (approved)

- Surface **both** runtime/error and HTTP access logs, both via the generated JSON logging config (rolled JSON files).
- **Live stream via SSE** (fetch + ReadableStream on the client), plus a snapshot GET.
- RBAC key **`caddy_logs:read`** (parallels `audit_logs:read`).
- Backfill **last 500 lines**; UI buffer cap **~3000 lines**.
- Rotation **10 MiB × 5 files, 7-day keep**.
- HTTP access logs only (no L4 access logs); global viewer with client-side filtering (not per-host monitoring).

## Architecture & files

- **Backend:** `config/builder.go` (+ `config/types.go` if the `LogConfig`/roll shape needs filling), `internal/config/config.go` (`CADDY_LOG_PATH`), `service/caddy_logs_service.go` + a log-tail reader, `handlers/caddy_logs_handler.go`, `routes/routes.go`, `rbac.yaml`. Tests alongside (builder, tailer, handler).
- **Infra:** `Dockerfile`, `docker-compose.yml`, possibly `docker/entrypoint.sh` (ensure the log dir exists/owned before Caddy starts).
- **Frontend:** `routes/_dashboard/caddy-logs.tsx` (+ overview/components under `components/caddy-logs/`), `hooks/use-caddy-logs.ts` (fetch-stream SSE client), `lib/router.tsx`, `components/layout/sidebar.tsx`, `types/caddy-logs.ts`.

## Decomposition (for the plan)

Subagent-driven, each independently gate-able:
1. **Caddy logging config** — populate `config.Logging` (runtime + access, JSON, rolled) + `CADDY_LOG_PATH` config + builder tests (config still validates; logging block correct).
2. **Log volume / Docker** — `Dockerfile` dir + ownership, `docker-compose.yml` volume, entrypoint dir-ensure.
3. **Tailer + snapshot endpoint** — the poll tailer (with rotation handling) + `GET /api/caddy-logs` snapshot + RBAC + route; tailer unit tests against a rotating temp file.
4. **SSE stream endpoint** — `GET /api/caddy-logs/stream` (backfill + live, disconnect cleanup).
5. **Frontend data layer** — `types/caddy-logs.ts` + `use-caddy-logs.ts` fetch-stream SSE client (start/stop/buffer/filter) + snapshot.
6. **Frontend page + nav** — `/dashboard/caddy-logs` route, tabs/live viewer/controls/filters, sidebar entry, router wiring.

## Testing

- **Backend:** Go unit tests — the builder (logging block present + config validates), the tailer (reads appends + handles rotation/truncation against a temp file), the handler (snapshot params, permission gating). Follow the existing testify patterns; integration tests where the repository/service pattern warrants.
- **Frontend:** gate (`pnpm --dir ui build` + `check` + `test`, 57 tests stay green); unit-test any pure helper (SSE frame parser, log-line formatter).
- The full Caddy-writes-→-tailer-reads loop is validated at the integration/manual level (a real Caddy in the container); unit tests cover the tailer against synthetic files.

## Risks & notes

- **Config-gen change is the highest risk** — it mutates the live config every proxy depends on. Must preserve generation/validation/reload; extend builder tests; verify a generated config-with-logging passes `caddy validate` and reloads.
- **SSE auth:** must use fetch + ReadableStream (EventSource can't send the Bearer header); never put the token in the query string.
- **Rotation handling:** the tailer must detect Caddy rolling the file (size shrink / new inode) and reopen, or it will silently stop after the first roll.
- **Log volume permissions:** Caddy (writer) and the Go backend (reader) run in the same container; ensure the dir is writable by Caddy and readable by the backend.
- **Access-log volume/perf:** access logging adds per-request overhead and can grow fast — rotation caps disk; the tailer streams incrementally (never loads whole files).
- **Disconnect cleanup:** each SSE connection starts a tailer goroutine; it must stop on client disconnect (request context) to avoid leaks.
