# External forward authentication and Authentik

This describes the implementation after `0.6.2+hotfix.1`. It is a configuration
and migration guide, not a record of a production rollout. The change was based
on source revision `76edc96b4244796dca59814581ec1217a2a9d3a9`.

## Request handling

Caddy checks the complete `verify_url` path and query with a GET request. The
original request method, scheme, host and URI are supplied in `X-Forwarded-*`
headers. Its POST/upload body stays available to the application. An empty
verification query clears the application's query on the subrequest.

HTTP outposts remain supported. HTTPS uses the URL hostname for certificate
verification/SNI and its authority (including an explicit port) for Host.
`X-Forwarded-Host` still identifies the application. Certificates must chain to
Caddy's system trust store; private CAs must be installed there by the operator.
There is no insecure TLS switch for external authentication. Dial and response
header timeouts are five and ten seconds respectively.

Every 2xx authentication response permits the application request. Selected
identity response headers replace request headers sent to the application;
missing/empty claims leave the corresponding header absent. Non-2xx status,
body, Location, and cookies pass back to the browser without a fallback login
redirect. Set-Cookie also passes through on success. Connection/TLS failures
return an error without contacting the application.

Before authentication or an IP/API exception, Caddy removes `X-Authentik-*`,
`X-Auth-*`, `Remote-User`, `Remote-Groups`, `Remote-Name`, `Remote-Email`,
`X-Forwarded-User`, and every configured `headers_to_copy` name. This applies
across the hostname's ACL assignments, including an earlier API exception.
Only headers actually returned by a successful verifier become trusted identity.
If Authorization is configured as a copied identity, the client's Authorization
is also removed; use this only for provider-generated application credentials.
Do not configure it when the verifier or application needs client credentials.

`headers_to_copy` is a list of literal HTTP header names; casing is normalized.
Wildcards, header renaming syntax, cookie, routing and hop-by-hop headers are
rejected. Empty/omitted lists use provider defaults (no identity headers for a
custom provider). Authentik defaults include Username, Groups, Email, Name, Uid,
Entitlements, Jwt and Meta-Jwks/Outpost/Provider/App/Version, all prefixed with
`X-Authentik-`. Custom claims must be listed explicitly.

## Radarr through NexusID: proposed configuration

Waygates at `192.168.150.28` is manually managed Docker Compose, outside Flux.
NexusID is `https://id.nexus.e412.in`. The following is an example for a future,
separately approved configuration change; no provider or ACL was created by
this implementation task. Use the real hostname/upstream of the existing Radarr
proxy in place of `https://radarr.example.com`.

1. In Authentik, create an application and a **Proxy Provider** using **Forward
   auth (single application)**. Set External host to
   `https://radarr.example.com`. Bind the intended access policy/groups and add
   this provider to the embedded or dedicated proxy outpost. Keep Radarr's own
   authentication and API-key checks enabled.
2. Create a Waygates access group, for example `Radarr — NexusID`, using `any`
   with one Authentik external provider and no IP bypass rules:

   ```json
   {
     "provider_type": "authentik",
     "name": "NexusID Radarr",
     "verify_url": "https://id.nexus.e412.in/outpost.goauthentik.io/auth/caddy",
     "outpost_url": "https://id.nexus.e412.in"
   }
   ```

   POST this body to `/api/acl/groups/{group_id}/providers`, or enter the same
   values on the group's External Providers tab. Leave Headers to Copy empty
   for defaults. A dedicated HTTP outpost can instead use
   `http://authentik-outpost:9000` for both origins, reachable from Caddy's
   container network. `outpost_url` is an optional HTTP(S) **origin**, without a
   path/query; omitted, null or empty uses the verification URL's origin.
3. Assign the group to the existing reverse proxy with `path_pattern: "/*"`,
   `priority: 100`, `enabled: true`. Preserve its existing Radarr upstream.
   All application paths, including JSON, media and scripts, require auth.
4. The renderer reserves `/outpost.goauthentik.io` and
   `/outpost.goauthentik.io/*` on that hostname and sends them to the outpost
   before application ACL routes. Callback, start, logout and outpost assets
   preserve their URI/query/method/body. They never reach Radarr and never call
   forward-auth recursively. The callback is normally
   `https://radarr.example.com/outpost.goauthentik.io/callback`; use the URL
   generated by the installed Authentik provider. Sign-out uses the outpost's
   `/outpost.goauthentik.io/sign_out` route. No application-wide exemption is
   needed. Similar-looking prefixes remain protected.
5. For an API client that cannot use browser SSO, add exceptions **only for the
   exact endpoints it requires**, after checking that Radarr rejects missing
   and incorrect API keys on those endpoints. For example, a movie-list client
   needs `/api/v3/movie`. Create a separate `Radarr API key` group with `any`
   and explicit IP `allow` rules for the client's addresses (or `0.0.0.0/0`
   and `::/0` only when API-key access from anywhere is intended). Assign it to
   `/api/v3/movie` at priority `10`. The matching request skips NexusID and
   reaches Radarr, where the `X-Api-Key` check must still run. Other API paths
   stay under the catch-all ACL. Add another exact assignment for each required
   endpoint; do not exempt `*.json`, `/api/*`, `/media/*`, or `/assets/*`.

Assignment priorities are ordered from lowest to highest; the first matching
terminal ACL route wins. A group with no methods does not create an exception.
These exceptions are explicit grants by that group, not additional conditions
on the catch-all group. Check priority ordering against existing assignments.
For Sonarr, use its own hostname, upstream, single-application provider and
endpoint exceptions; do not share application-specific policy accidentally.

A hostname supports one outpost origin. Conflicting Authentik origins fail
closed with 503 for that hostname. Even a path-scoped Authentik assignment needs
the host-level callback namespace. Do not use that namespace for application
content or assign different single-app providers to paths of the same host.

## Migration and compatibility

- Migration `000014_add_acl_outpost_url` adds a nullable column. Existing
  Authentik providers derive the outpost origin from `verify_url`. Back up the
  database before a separately approved upgrade. The down migration removes
  only this column; reverting code also restores the old security defects.
- `auth_redirect_url` is **deprecated and ignored**. Stored values and API
  reads/writes remain compatible, but the UI no longer offers the field. It
  never controlled the old renderer. Configure redirects in the auth provider;
  401, 403, 429 and 5xx are not converted into login redirects.
- Automatic static-resource exceptions are removed for **every ACL mode and
  provider**, including Basic and Waygates auth. Existing public JSON, media,
  favicon, assets and `.well-known` application paths now require authentication.
  Review deliberately public paths and add only explicit ACL assignments.
- Waygates' own login page, built assets, branding API and login/session/OAuth
  APIs are served by the management application on its own hostname. Keep that
  login origin reachable without the ACL that redirects to it. Removing
  exceptions on a protected Radarr/Sonarr hostname does not affect assets
  fetched from the management hostname. Do not protect the entire management
  hostname with its own login ACL: that creates a loop. Any custom branding
  assets hosted on a protected application also need an explicit public route
  or a separate public origin.
- `ACL_WAYGATES_VERIFY_URL` retains its existing **base URL** semantics:
  `/api/auth/acl/verify` is appended by the renderer. Waygates still redirects
  401 to its configured login page, returns 403 for denial, and fails closed
  when verification is unavailable. It now benefits from GET/body/TLS and
  request identity handling too.
- Existing mode selection remains: in `any` and `ip_bypass`, matching allow or
  bypass IPs grant access after deny rules; otherwise the selected auth handler
  runs. In `all`, allow/bypass IPs restrict the permitted network and the
  selected auth handler must still succeed. Deny rules take precedence within
  that assignment. Unmatched IP-only rules retain their existing behavior.
- The renderer still selects the **first external provider** and gives it
  precedence over Waygates/Basic auth. It does not compose multiple external
  providers or external and internal identity checks with AND/OR. Use one
  external provider per group. `all` does not turn this into a provider chain.
- Invalid stored provider URLs and missing ACL groups now fail closed rather
  than skipping protection. New/updated URLs must be literal absolute HTTP(S)
  URLs without credentials/fragments/placeholders and with a valid port.
- Protect direct access to application listeners separately; ACL protection
  applies to traffic through Waygates. This task does not change app listeners,
  application authentication, network policy, live ACLs or deployment state.

## Verification

The integration suite starts a real Caddy process with generated JSON,
`admin.disabled: true`, automatic HTTPS disabled, loopback listeners and private
temporary storage. It runs `caddy validate` on every test configuration. Mock
auth and upstream servers exercise wire behavior; a generated local certificate
checks trusted HTTPS, hostname/SNI/Host, and rejection of untrusted or mismatched
certificates. No production auth endpoint is used.

```sh
CADDY_BINARY=/absolute/path/to/caddy go test ./backend/internal/caddy/config \
  -run 'TestCaddy(ExternalForwardAuth|ForwardAuth)' -count=1 -v
```

CI extracts the binary from its freshly built test image and runs these tests
with backend coverage. Use Caddy **2.11.3**, pinned by this repository's Dockerfile. Without
`CADDY_BINARY`, these process integration tests report a skip; `-short` also
skips them. Run backend unit/model/service/API/repository tests and UI checks as
part of the same review. See the validation record below for actual results.

No suitable isolated Authentik installation was available. The mocks do not
prove a real NexusID login/consent/callback session or installed Authentik policy
behavior. An isolated Authentik browser test and an owner-approved staged
rollout remain necessary before assigning production ACLs.
